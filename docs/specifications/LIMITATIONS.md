# Technical Limitations

An honest list of what BigO Lens cannot do, does not do yet, or does only approximately. Each limitation states its
effect on results and whether a milestone addresses it. When in doubt, the analyzer reports `unknown` or
`unsupported` rather than guessing.

Related: [ANALYSIS_MODEL.md](../design/ANALYSIS_MODEL.md) · [COMPLEXITY_MODEL.md](COMPLEXITY_MODEL.md) ·
[CONSTRAINT_MODEL.md](CONSTRAINT_MODEL.md) · [FAQ.md](../user/FAQ.md) · [TROUBLESHOOTING.md](../development/TROUBLESHOOTING.md)

## 1. Undecidability

Whether a program terminates — and therefore how many iterations a loop performs — is undecidable in general
(halting problem; Rice's theorem for any non-trivial semantic property). BigO Lens therefore recognises a **finite
set of syntactic loop forms** ([COMPLEXITY_MODEL.md §2](COMPLEXITY_MODEL.md#2-supported-loop-forms)) and reports
everything else as `unknown`. Coverage is permanently `partial`; no future milestone removes this limit, only
widens the recognised set.

## 2. Data-dependent loops

Loops whose trip count depends on values computed or read during execution are `unknown`:

- binary search `while (lo < hi)`, two-pointer loops, BFS/DFS `while (!q.empty())`, Collatz-style loops;
- loops bounded by array elements (`j < a[i]`), function results, or range-for element values;
- `for` loops without all three clauses.

Amortised arguments (e.g. two pointers moving monotonically, total O(n)) are not recognised. One unknown loop
inside a nest makes the **whole nest** `unknown`, including an enclosing `while (t--)` test-case wrapper.

## 3. Interprocedural analysis

Not implemented (M2 follow-up). A loop nest that calls a user-defined function is downgraded to `estimated`, and the
callee's cost is **not included** in the count. A function call outside any loop produces no finding at all, so
heavy work in a helper called once is invisible to the time summary.

## 4. Recursion

Direct self-recursion is **detected** and reported as `unsupported` with no time expression; recurrence solving is
planned ([COMPLEXITY_MODEL.md §9](COMPLEXITY_MODEL.md#9-recursion)). Mutual recursion is not detected. Stack depth
and stack memory of recursion are not estimated.

## 5. Standard-library costs not applied

Library calls in a loop (`std::sort`, `map::find`, `push_back`, `lower_bound`, …) are listed in `limitations`, but
their cost is **not** multiplied into the structural count. A loop of `n` iterations calling `std::sort` on `n`
elements is reported as `n` (with a limitation), not `n² log n`. The STL cost table exists and is exposed through
`capabilities` (`data_only`) but is not applied. Overloaded operators (including `std::cin >>`) and constructors are
not listed. `unordered_map` worst cases (O(n) per operation under adversarial hashing) are recorded in the table only.

## 6. Templates and macros

- Only template **primaries** are analysed, not instantiations: costs that depend on template arguments are seen in
  their generic form.
- Macros are analysed after expansion; locations are mapped to the expansion site, so a finding inside a macro such
  as `#define FOR(i, n) for (int i = 0; i < (n); ++i)` points at the macro use, not the macro definition. Loops
  generated by macros are analysed like hand-written loops.
- Constant expressions are evaluated by Clang; `const`/`constexpr` bounds become constants.

## 7. Inline assembly and non-standard code

Inline assembly, compiler intrinsics and builtins are treated as opaque calls (they may appear as library calls in
limitations). Code that only compiles with non-default extensions or headers absent on the user's machine (e.g.
`<bits/stdc++.h>` on a toolchain that lacks it) fails with `source_parse_error`; analysis never runs on an AST with
errors.

## 8. Undefined behaviour

Analysis assumes the program has defined behaviour. Signed overflow of a loop index, out-of-bounds access, or a
bound that changes through aliasing (a pointer or reference to the bound variable) can make real executions differ
from the model. Writes through pointers/references are detected only when they are visible as modifications of the
variable in the loop body; aliasing through other names is not tracked.

## 9. Compiler optimisations

The structural count describes the source as written. Optimising compilers can hoist, vectorise, unroll, or
eliminate loops entirely (e.g. a loop with no observable effect, or a closed-form replacement of a summation). The
count is therefore an upper bound on source-level iterations, not a prediction of executed machine instructions.

## 10. Hardware and runtime variance

No implemented feature produces a runtime. When benchmarking exists (M4), measured times depend on CPU, frequency
scaling, caches, memory bandwidth, OS scheduling, compiler version and flags; a judge machine may differ
substantially from the user's machine. Runtime estimates will be ranges with stated assumptions, never guarantees.

## 11. Memory: lower bounds only

- Static storage is exact; everything else is partial.
- Sized `std::vector<T>(count, …)` counts only the element buffer; capacity slack, allocator overhead and nested
  ownership (`vector<vector<int>>`, `vector<string>`) are not followed.
- `push_back`-grown containers, `new`, `map`/`set` nodes, strings, and stack frames are not modelled.
- The estimated minimum assumes each sized vector is constructed once at its largest single-instance size and that
  all of them are live simultaneously. Lifetimes are not analysed, so two vectors that never coexist are still added.
- Consequently memory feasibility is only ever `high_risk` or `unknown` from static analysis.

## 12. Name-based constraint binding

Constraints bind to symbolic variables **by identifier name** ([CONSTRAINT_MODEL.md §2](CONSTRAINT_MODEL.md#2-variable-binding)).
Pitfalls:

- **Shadowing / reuse:** a global `n` and a local `n`, or `n` in two functions, receive the same bounds.
- **Renamed copies:** `int len = n; for (i < len)` produces variable `len`; a constraint on `n` does not apply and
  `len` appears in `missing_bounds`.
- **Unused names:** a constraint whose name matches no expression variable has no effect and no warning is given in
  protocol 1.0.
- **Containers:** `v.size()` and `v.length()` both bind to `"v.size()"`; constraining `n` does not constrain
  `v.size()` even if `v` was constructed with `n` elements.
- **Value changes:** the bound value is assumed to be the one at loop entry; a bound variable written inside the loop
  makes the result `estimated`.

## 13. Constraint relationships

- Product and linear constraints are validated but **not used** to tighten bounds; results stay sound but can be
  much larger than the true worst case (an assumption is attached).
- Sum constraints over different count variables in one expression → `unknown`.
- Concave per-case costs (√n, log n) under sum constraints use a sound but loose fallback.
- Lower bounds are never used to produce lower-bound workloads.

## 14. Numeric evaluation

Workloads are IEEE doubles; values above 2⁵³ are approximate. Non-finite results become `unknown` (overflow).
Non-affine summations are evaluated term by term under a budget (5·10⁷ node evaluations); larger ones become
`unknown`.

## 15. Platform support

| Platform | Core engine and tests | Clang frontend (`analyze`) | Notes |
| --- | --- | --- | --- |
| Linux (Ubuntu) | Supported, CI | Supported — primary platform (LLVM/Clang 18 in CI; developed with Clang 20) | Full build |
| macOS | Supported, CI (without frontend) | **Experimental** with Homebrew LLVM; CI job allowed to fail | |
| Windows | Supported, CI (MSVC, `BIGOLENS_ENABLE_CLANG=OFF`) | **Experimental / untested** | Without the frontend `analyze` returns `frontend_unavailable` |

The VS Code extension's CI smoke test runs on Linux only. Release workflow packages the engine for Linux only.

## 16. Benchmarking is not implemented and, when it is, not sandboxed until isolation exists

The `benchmark` action returns `not_implemented`. When M4 adds execution, the compiled user program will run on the
user's machine. Timeouts, rlimits and process-tree cleanup limit resource use but **are not a sandbox**: until the
per-platform isolation in [BENCHMARK_SPECIFICATION.md §11](BENCHMARK_SPECIFICATION.md#11-isolation-per-platform-planned)
is implemented and verified, benchmarking is documented and presented as **not sandboxed**. Only benchmark code you
would be willing to run yourself. See [SECURITY.md](../../SECURITY.md).

## 17. Parsing reads local headers

Static analysis does not execute code, but Clang reads the headers named in `#include` from the local filesystem,
as a compiler would. Analysing untrusted source can therefore read (not execute) local header files, and very large
or pathological sources can consume CPU and memory up to the extension's timeout.

## 18. Scope

Single translation unit, C++ only. Multi-file projects, other languages, and build-system integration are out of
scope ([DESIGN.md §9](../../DESIGN.md#9-non-goals)).
