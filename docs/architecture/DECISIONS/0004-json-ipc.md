# ADR 0004: Use versioned JSON over stdin and stdout, one process per request

- **Status:** Accepted
- **Date:** 2026-11-10

## Context

The TypeScript extension ([ADR 0003](0003-typescript-extension.md)) must call the native engine ([ADR 0002](0002-separate-native-engine.md)). The channel must:

- Work on Linux, macOS and Windows without network sockets.
- Be easy to test from a shell and from CI.
- Be strictly validated on both sides.
- Be able to evolve without silent incompatibility.

## Decision

1. **Transport.** The client spawns `bigolens-engine` with `shell: false` and **no arguments**, writes **one** JSON request to stdin and closes it. The engine writes **one** JSON response line to stdout. `--request FILE` exists for manual use and tests.
2. **One process per request.** The engine is stateless and exits after responding. The client enforces a timeout (`bigoLens.analysisTimeoutMs`, default 30000) by killing the process, and caps stdout at 16 MiB.
3. **Exit codes.** 0 whenever a response was written, including error responses. 2 for usage errors. 1 otherwise.
4. **Limits.** The engine accepts requests up to 4 MiB and source content up to 2 MiB. JSON nesting deeper than 64 levels is rejected before the recursive parser runs. Unknown fields are rejected. Integers must have magnitude at most 1e18.
5. **Contract.** The protocol is defined by `shared/schemas/request.schema.json` and `response.schema.json` (JSON Schema draft 2020-12). The engine validates in `api::parseRequest`. The extension validates every response with ajv against copies of the same schemas.
6. **Versioning.** `schema_version` is `"MAJOR.MINOR"`. The engine accepts a request **only if it has the same major version and a minor version less than or equal to the engine's**. Otherwise it returns `unsupported_schema_version`. Rules for changing the schema:
   - A minor version may add optional request fields, or response fields that old clients can ignore.
   - A major version is required for removals, renames, changes of type or meaning, and new required request fields.
   - Responses always carry `engine.protocol_version`, so a client can detect an older engine.
7. **Errors are data.** Every failure becomes `status: "error"` with stable `errors[].code` values (`malformed_json`, `request_too_large`, `invalid_request` with a JSON-pointer `path`, `unsupported_schema_version`, `not_implemented`, `frontend_unavailable`, `source_parse_error`, `internal_error`). The `request_id` is echoed whenever it can be recovered.

## Alternatives considered

| Alternative | Why it was rejected for now |
|---|---|
| Persistent engine server (JSON-RPC over stdio) | Saves start-up time, but adds lifecycle management (crash recovery, cancellation, memory growth across requests, state leaks between files). Analysis is on demand, so start-up cost is acceptable today. |
| Language Server Protocol | Same lifecycle costs, plus document synchronisation semantics that BigO Lens does not need yet. The results do not map naturally onto LSP's data model (workloads, assumptions, feasibility). |
| TCP or HTTP localhost server | Opens a network surface, needs port management, and raises firewall and security concerns. |
| Command-line arguments for input | Length limits, quoting and escaping problems, and a shell-injection risk. |
| Binary formats (protobuf, MessagePack) | Harder to debug and to inspect in tests. JSON is fast enough for 4 MiB inputs. |

## Consequences

**Positive**

- Simple, debuggable and testable: `bigolens-engine --request shared/examples/analyze.request.json`.
- Strong isolation. A timeout kill always reclaims resources, and no state survives between requests.
- An explicit compatibility rule, with schemas shared by both sides.

**Negative**

- Each request pays the cost of starting a process and initialising Clang.
- No streaming of partial results and no cooperative cancellation. Cancellation means killing the process.
- The schemas must be kept identical in `shared/schemas/` and `extension/schemas/`. They are copied at build time.

## Follow-up considerations

- Revisit a persistent server or LSP mode when real-time analysis while typing is planned, or when measured start-up latency becomes a usability problem ([PERFORMANCE](../../engineering/PERFORMANCE.md)). Any such mode must keep the same message schemas.
- Benchmark requests (M4) may run much longer. Progress reporting may justify a streaming extension in a later major or minor version.
- Check example responses into `shared/examples/` next to the requests, generated by running the engine.
